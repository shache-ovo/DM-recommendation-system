# 전처리 결정과 근거

`scripts/preprocess.py`가 적용하는 규칙과 그렇게 정한 이유다.
설정값은 `configs/default.yaml`에 있고, 값을 바꿔 다시 실행하면 산출물이 바뀐다.
근거 수치는 `docs/eda.md`와 `reports/tables/preprocess_alternatives.csv`(`python3 scripts/preprocess_alternatives.py`)에서 가져왔다.

## 적용 순서와 결과

| 순서 | 규칙 | 상호작용 | 사용자 | 레시피 |
|---|---|---|---|---|
| 0 | 원본 | 1,132,367 | 226,570 | 231,637 |
| 1 | 칼로리가 0이거나 전체 99.9% 분위수(8,291.0)를 넘는 레시피 제거 | 1,131,241 | 226,330 | 231,352 |
| 2 | 평점 4 이상만 양성으로 | 1,002,781 | 180,144 | 217,299 |
| 3 | 5-core | 498,200 | 16,032 | 37,819 |
| 4 | 사용자별 시간순 분할 | train 466,136 / valid 16,029 / test 16,028 | 16,032 | 37,818 |

단계별 수치는 `reports/tables/preprocess_steps.csv`에 기록된다.

## 결정 요약

| 항목 | 값 | 설정 키 | 상태 |
|---|---|---|---|
| 피드백 유형 | implicit | — | 확정 |
| 양성 기준 | 평점 4 이상 | `preprocess.positive_min_rating` | 팀 확인 필요 |
| 평점 0~3 | 양성에서 제외, "본 레시피"로 보존 | `preprocess.keep_non_positive_rows` | 팀 확인 필요 |
| 칼로리 이상치 | 0 또는 99.9% 분위수 초과 제거 | `preprocess.calorie_max_quantile`, `remove_zero_calories` | 팀 확인 필요 |
| 최소 상호작용 수 | 5-core | `preprocess.k_core` | 팀 확인 필요 |
| 분할 | 사용자별 시간순, test 1건, valid 1건 | `split.*` | 팀 확인 필요 |
| 평가 대상 | train에 등장한 사용자·레시피만 | `split.restrict_eval_to_train` | 확정 (cold 미고려) |

## 1. 양성 기준: 평점 4 이상

- 평점 분포는 5점 72.09%, 4점 16.55%, 3점 3.61%, 2점 1.25%, 1점 1.13%, 0점 5.37%다.
- 평점 1~3은 67,796건(6.0%)이다. 이를 양성으로 넣으면 사용자가 낮게 평가한 레시피를 선호로 학습한다.
- 평점 0은 별점 없이 글만 남긴 리뷰다. 무작위 6건을 읽었을 때 칭찬과 불만이 섞여 있었다. 표본이 작아 비율은 알 수 없고, 일괄적으로 긍정이나 부정으로 볼 근거가 없다는 점만 확인했다.
- 따라서 평점 0~3은 양성에서 빼되 지우지 않는다. 사용자가 이미 본 레시피이므로 `interactions_seen_non_positive.csv`에 남겨 추천 후보와 negative 샘플에서 제외하는 데 쓴다.

대안: 모든 상호작용을 양성으로 보는 방법(`positive_min_rating: 0`). 5-core 기준 상호작용이 555,206건으로 11% 늘지만 위의 문제가 생긴다.

## 2. 칼로리 이상치: 0 또는 99.9% 분위수 초과 제거

- 칼로리의 중앙값은 313.4인데 최대값은 434,360.2다. 최상위 레시피는 대용량 술, 케이크, 믹스 가루로, 값이 틀렸다기보다 레시피 전체 분량의 합계로 보인다. 원출처는 1회 제공량 기준을 설명하지 않는다.
- 명백한 경우만 제거한다. 99.9% 분위수 초과 232개와 칼로리 0인 53개, 합쳐 285개(0.12%)다.
- 기준을 느슨하게 잡은 이유는 5-core가 이미 대부분의 극단값을 걸러내기 때문이다. 추천 대상 레시피의 칼로리는 중앙값 295.7, 99% 분위수 3,014.1, 최대 8,024.1이다.
- 남은 긴 꼬리는 제거가 아니라 변환으로 다룬다. k-means 입력에는 표준화 전에 로그 변환이나 절단이 필요하다. 건강 지표는 분위수 순위를 쓰므로 영향이 작다.
- 분위수는 레시피 속성만으로 계산한다. 상호작용을 쓰지 않으므로 평가 정보가 새지 않는다.

한계: 1회 제공량을 알 수 없어서 칼로리와 PDV를 레시피 간에 엄밀히 비교할 수 없다. 이 프로젝트의 건강 지표는 절대 기준이 아니라 분포 안에서의 상대 위치를 쓴다.

## 3. 최소 상호작용 수: 5-core

원본에서 사용자의 73.4%는 상호작용이 1건뿐이고 89.8%는 5건 미만이다. cold 사용자·레시피를 다루지 않으므로 걸러내야 한다.
모든 사용자와 레시피가 양성 k건 이상을 가질 때까지 반복해서 제거한다.

| k | 상호작용 | 사용자 | 레시피 | 분할 후 사용자당 train (최소 / 중앙값) |
|---|---|---|---|---|
| 3 | 660,297 | 28,997 | 73,925 | 1 / 4 |
| **5** | **498,200** | **16,032** | **37,819** | **3 / 8** |
| 10 | 273,659 | 6,704 | 11,592 | 8 / 17 |

- k = 3이면 사용자당 2건을 평가용으로 떼고 나서 train이 1건만 남는 사용자가 생긴다. 사용자 벡터를 학습하기에도, 재료 유사 검색의 기준 레시피로 쓰기에도 부족하다.
- k = 10이면 k = 5에 비해 사용자가 58% 줄고 레시피가 11,592개로 줄어, 근사 검색(LSH)을 쓸 이유가 약해진다.
- k = 5는 train이 최소 3건 남는 가장 작은 값이다.

한계: 5-core 뒤에 남는 사용자는 양성 평가를 남긴 사용자의 8.9%다. 활동이 많은 사용자에 대한 결과이므로 전체 사용자로 일반화할 수 없다.

## 4. 분할: 사용자별 시간순

사용자별로 날짜순 정렬해 마지막 양성 1건을 test, 그 앞 1건을 validation, 나머지를 train으로 둔다.

5-core 기준으로 두 방식을 비교했다.

| 방식 | 평가 가능한 사용자 | test 중 사용자·레시피가 모두 train에 있는 비율 |
|---|---|---|
| **사용자별 시간순** | **16,028** | **99.98%** |
| 전체 시간 기준 80/10/10 | 4,336 | 67.45% |

- 이 데이터의 활동은 2008년에 가장 많고 이후 줄어든다. 전체 시간 기준으로 자르면 train은 2010-06-24까지, test는 2012-04-02 이후가 되어 test의 3분의 1이 train에 없는 사용자나 레시피다. cold를 다루지 않는다는 전제와 맞지 않는다.
- validation을 따로 둔 이유: 가이드라인이 test를 모델 선택과 분리하라고 요구한다. 하이퍼파라미터와 λ는 validation으로 고른다.
- 날짜가 일 단위라서 5-core 사용자의 약 10%는 마지막 날에 양성이 2건 이상이다. 같은 날의 순서는 원본 파일의 행 순서로 정한다. 실행할 때마다 같은 결과가 나온다.
- train에 한 번도 나오지 않는 레시피가 정답인 경우(validation 3건, test 4건)는 평가에서 뺀다.

한계: 어떤 사용자의 test 시점보다 나중에 일어난 다른 사용자의 기록이 train에 들어 있다. 실제 서비스의 시간 흐름과 다르다.

## 5. 파싱

- `nutrition`: 값 7개의 리스트를 컬럼 7개로 펼친다. 순서는 원출처의 컬럼 설명을 따른다(`docs/data_source.md`). 모든 레시피가 정확히 7개 값을 가진다.
- `ingredients`, `tags`: 원본은 파이썬 리스트 표기 문자열이다. JSON 리스트 문자열로 다시 쓴다. 이름은 바꾸지 않는다.
- 재료 이름의 정규화(표기 변형, 고빈도 재료)는 전처리가 아니라 MinHash 입력을 만드는 단계에서 한다. 영양·태그를 쓰는 쪽에 영향을 주지 않기 위해서다.
- `steps`, `description`, `contributor_id`, `submitted`, 리뷰 본문은 쓰지 않으므로 산출물에 넣지 않는다.
- 결측: 쓰는 컬럼 중에는 레시피 `name` 1건뿐이고 그대로 둔다.

## 6. 재현성

- 무작위 요소가 없다. 같은 원본과 설정이면 산출 파일이 바이트 단위로 같다(두 번 실행해 sha256으로 확인).
- 5-core 결과는 별도 구현으로 다시 계산해 같은 값(498,200건 / 16,032명 / 37,819개)을 얻었다.
- 스크립트는 저장 전에 불변식을 검사한다. 분할 사이의 (사용자, 레시피) 중복 없음, 평가 집합의 사용자·레시피가 모두 train에 있음, 시간 순서, 평점 범위, 인덱스의 연속성이다.
